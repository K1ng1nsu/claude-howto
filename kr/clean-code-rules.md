# AI 코드 생성을 위한 클린 코드 규칙

이 규칙들은 유지보수 가능하고 전문적인 품질의 코드를 생성하도록 안내합니다.

## 의미 있는 이름
- 존재 이유를 설명하는 의도가 드러나는 이름을 사용합니다
- 잘못된 정보와 의미 없는 구분을 피합니다 (예: `data`, `info`, `manager`)
- 발음 가능하고 검색 가능한 이름을 사용합니다
- 클래스 이름: 명사 (예: `UserAccount`, `PaymentProcessor`)
- 메서드 이름: 동사 (예: `calculateTotal`, `sendEmail`)
- 정신적 매핑과 인코딩을 피합니다 (헝가리안 표기법, 접두사)

## 함수
- 함수는 작게 유지합니다 (이상적으로 20줄 미만)
- 한 가지만 수행합니다 - 단일 책임 원칙
- 함수당 하나의 추상화 수준
- 인자 제한: 0-2개가 이상적, 최대 3개, 플래그 인자 금지
- 부수 효과 없음 - 함수는 이름이 말하는 대로만 수행해야 함
- 명령(상태 변경)과 조회(정보 반환)를 분리
- 오류 코드보다 예외를 선호

## 주석
- 코드는 자명해야 함 - 가능하면 주석을 피합니다
- 좋은 주석: 법적 정보, 경고, TODO, 공개 API 문서
- 나쁜 주석: 중복, 오해의 소지, 또는 나쁜 코드 설명
- 코드를 절대 주석 처리하지 말고 삭제하세요 (버전 컨트롤이 히스토리를 보존)
- 주석이 필요하다면 코드 리팩토링을 고려하세요

## 형식
- 파일을 작고 집중적으로 유지
- 수직 형식: 관련 개념은 가깝게, 빈 줄로 개념 구분
- 수평 형식: 줄 길이 제한 (80-120자)
- 일관된 들여쓰기와 팀 스타일 사용
- 관련 함수를 함께 그룹화

## 객체와 데이터 구조
- 객체: 추상화 뒤에 데이터를 숨기고 메서드를 통해 동작 노출
- 데이터 구조: 데이터를 노출하고 최소한의 동작만 가짐
- 데메테르 법칙: 직접적인 친구하고만 대화하고 `a.getB().getC().doSomething()` 금지
- getter/setter로 내부 구조를 맹목적으로 노출하지 마세요

## 오류 처리
- 반환 코드나 오류 플래그 대신 예외 사용
- 코드가 실패할 수 있는 경우 `try-catch-finally`를 먼저 작성
- 예외 메시지에 컨텍스트 제공
- `null`을 반환하지 마세요 - 빈 컬렉션이나 Optional/Maybe 사용
- 인자로 `null`을 전달하지 마세요

## 클래스
- 작은 클래스: 줄 수가 아닌 책임으로 측정
- 단일 책임 원칙: 변경할 이유가 하나
- 높은 응집도: 많은 메서드에서 사용하는 클래스 변수
- 낮은 결합도: 클래스 간 최소 의존성
- 개방-폐쇄 원칙: 확장에는 열려 있고 수정에는 닫혀 있음

## 단위 테스트
- 빠르고, 독립적이며, 반복 가능하고, 자체 검증 가능하며, 적시에 작성 (F.I.R.S.T.)
- 테스트당 하나의 단언 (또는 하나의 개념)
- 테스트 코드 품질은 프로덕션 코드 품질과 동등
- 무엇을 테스트하는지 설명하는 읽기 쉬운 테스트 이름
- 준비-실행-단언 패턴

## 코드 품질 원칙
- **DRY (Don't Repeat Yourself)**: 중복 없음
- **YAGNI (You Aren't Gonna Need It)**: 가상의 미래를 위해 구축하지 마세요
- **KISS (Keep It Simple)**: 불필요한 복잡성 방지
- **Boy Scout Rule**: 발견한 코드보다 더 깨끗하게 남기고 떠나세요

## 피해야 할 코드 냄새
- 긴 함수 또는 클래스
- 중복 코드
- 데드 코드 (사용되지 않는 변수, 함수, 매개변수)
- 기능 선망 (다른 클래스에 더 관심이 많은 메서드)
- 부적절한 친밀감 (클래스가 서로에 대해 너무 많이 알고 있음)
- 긴 매개변수 목록
- 원시 타입 중독 (작은 객체 대신 원시 타입을 과도하게 사용)
- switch/case 문 (다형성 고려)
- 임시 필드 (가끔만 사용되는 클래스 변수)

## 동시성
- 동시성 코드를 다른 코드와 분리
- 동기화/잠금 데이터의 범위 제한
- 스레드 안전 컬렉션 사용
- 동기화 섹션을 작게 유지
- 실행 모델과 프리미티브를 숙지

## 시스템 설계
- 생성과 사용을 분리 (의존성 주입)
- 복잡한 객체 생성에는 팩토리, 빌더 사용
- 구현이 아닌 인터페이스에 프로그래밍
- 상속보다 컴포지션 선호
- 단순화할 때 디자인 패턴 적용, 과시용으로 사용하지 마세요

## 리팩토링
- 큰 배치가 아닌 지속적으로 리팩토링
- 전후에 항상 통과하는 테스트 유지
- 작은 단계: 한 번에 하나의 변경
- 일반적인 리팩토링: 메서드 추출, 이름 변경, 이동, 인라인

## 문서
- 자기 문서화 코드 > 주석 > 외부 문서
- 공개 API는 명확한 문서 필요
- 문서에 예제 포함
- 문서를 코드 가까이 유지 (이상적으로는 코드 내에)

---

**핵심 철학**: 코드는 작성되는 것보다 10배 더 많이 읽힙니다. 영리함보다 가독성과 유지보수성을 최적화하세요.

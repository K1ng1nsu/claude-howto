## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다 (비어 있지 않은 경우). 사용자는 다음을 지정할 수 있습니다:
- `create` - 처음부터 새 CLAUDE.md 생성
- `update` - 기존 CLAUDE.md 개선
- `audit` - 현재 CLAUDE.md 품질 분석 및 보고
- 생성/업데이트할 특정 경로 (예: 디렉토리별 지침을 위한 `src/api/CLAUDE.md`)

## 핵심 원칙

**LLM은 상태 비저장**: CLAUDE.md는 모든 대화에 자동으로 포함되는 유일한 파일입니다. 이는 코드베이스에 AI 에이전트를 온보딩하는 주요 문서 역할을 합니다.

### 황금 규칙

1. **적을수록 좋다**: 최첨단 LLM은 약 150-200개의 지침을 따를 수 있습니다. Claude Code의 시스템 프롬프트는 이미 약 50개를 사용합니다. CLAUDE.md를 집중적이고 간결하게 유지하세요.

2. **보편적 적용 가능성**: 모든 세션에 관련된 정보만 포함하세요. 작업별 지침은 별도 파일에 속합니다.

3. **Claude를 린터로 사용하지 마라**: 스타일 가이드라인은 컨텍스트를 부풀리고 지침 수행 능력을 저하시킵니다. 대신 결정론적 도구(prettier, eslint 등)를 사용하세요.

4. **절대 자동 생성하지 마라**: CLAUDE.md는 AI 하네스의 가장 높은 레버리지 포인트입니다. 신중한 고려와 함께 수동으로 작성하세요.

## 실행 흐름

### 1. 프로젝트 분석

먼저 현재 프로젝트 상태를 분석합니다:

1. 기존 CLAUDE.md 파일 확인:
   - 루트 레벨: `./CLAUDE.md` 또는 `.claude/CLAUDE.md`
   - 디렉토리별: `**/CLAUDE.md`
   - 전역 사용자 설정: `~/.claude/CLAUDE.md`

2. 프로젝트 구조 식별:
   - 기술 스택 (언어, 프레임워크)
   - 프로젝트 유형 (모노레포, 단일 앱, 라이브러리)
   - 개발 도구 (패키지 매니저, 빌드 시스템, 테스트 러너)

3. 기존 문서 검토:
   - README.md
   - CONTRIBUTING.md
   - package.json, pyproject.toml, Cargo.toml 등

### 2. 콘텐츠 전략 (무엇, 왜, 어떻게)

CLAUDE.md를 세 가지 차원으로 구성:

#### 무엇 - 기술 및 구조
- 기술 스택 개요
- 프로젝트 구성 (특히 모노레포에서 중요)
- 주요 디렉토리 및 그 목적

#### 왜 - 목적 및 컨텍스트
- 프로젝트가 하는 일
- 특정 아키텍처 결정이 내려진 이유
- 각 주요 컴포넌트의 책임

#### 어떻게 - 워크플로우 및 규칙
- 개발 워크플로우 (bun vs node, pip vs uv 등)
- 테스트 절차 및 커맨드
- 검증 및 빌드 방법
- 중요한 "주의사항" 또는 명확하지 않은 요구사항

### 3. 점진적 공개 전략

대규모 프로젝트의 경우 `agent_docs/` 폴더 생성을 권장:

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

CLAUDE.md에서 다음과 같은 지침으로 이러한 파일을 참조:
```markdown
자세한 빌드 지침은 `agent_docs/building_the_project.md`를 참조하세요
```

**중요**: 오래된 컨텍스트를 피하기 위해 코드 스니펫 대신 `file:line` 참조를 사용하세요.

### 4. 품질 제약 조건

CLAUDE.md를 생성하거나 업데이트할 때:

1. **목표 길이**: 300줄 미만 (가급적 100줄 미만)
2. **스타일 규칙 없음**: 린팅/포맷팅 지침 제거
3. **작업별 지침 없음**: 별도 파일로 이동
4. **코드 스니펫 없음**: 파일 참조 사용
5. **중복 정보 없음**: package.json 또는 README에 있는 내용 반복 금지

### 5. 필수 섹션

잘 구조화된 CLAUDE.md는 다음을 포함해야 합니다:

```markdown
# 프로젝트 이름

간단한 한 줄 설명.

## 기술 스택
- 주요 언어 및 버전
- 주요 프레임워크/라이브러리
- 데이터베이스/저장소 (있는 경우)

## 프로젝트 구조
[모노레포 또는 복잡한 구조에만 해당]
- `apps/` - 애플리케이션 진입점
- `packages/` - 공유 라이브러리

## 개발 커맨드
- 설치: `command`
- 테스트: `command`
- 빌드: `command`

## 중요 규칙
[명확하지 않고 영향력이 큰 규칙만]
- 간단한 설명과 함께 규칙 1
- 간단한 설명과 함께 규칙 2

## 알려진 이슈 / 주의사항
[개발자를 일관되게 당황하게 하는 것들]
- 이슈 1
- 이슈 2
```

### 6. 피해야 할 안티 패턴

**포함하지 말 것:**
- 코드 스타일 가이드라인 (린터 사용)
- Claude 사용 방법에 대한 문서
- 명백한 패턴의 긴 설명
- 복사-붙여넣기 코드 예제
- 일반적인 모범 사례 ("깨끗한 코드 작성")
- 특정 작업에 대한 지침
- 자동 생성된 콘텐츠
- 광범위한 TODO 목록

### 7. 검증 체크리스트

마무리하기 전에 확인:

- [ ] 300줄 미만 (가급적 100줄 미만)
- [ ] 모든 줄이 모든 세션에 적용됨
- [ ] 스타일/포맷팅 규칙 없음
- [ ] 코드 스니펫 없음 (파일 참조 사용)
- [ ] 커맨드가 작동하는 것으로 확인됨
- [ ] 복잡한 프로젝트에 점진적 공개 사용
- [ ] 중요한 주의사항 문서화됨
- [ ] README.md와 중복 없음

## 출력 형식

### `create` 또는 기본:

1. 프로젝트 분석
2. 위 구조를 따르는 CLAUDE.md 초안 작성
3. 검토를 위해 초안 제시
4. 승인 후 적절한 위치에 작성

### `update`:

1. 기존 CLAUDE.md 읽기
2. 모범 사례에 따라 감사
3. 식별:
   - 제거할 콘텐츠 (스타일 규칙, 코드 스니펫, 작업별)
   - 압축할 콘텐츠
   - 누락된 필수 정보
4. 검토를 위해 변경사항 제시
5. 승인 후 변경사항 적용

### `audit`:

1. 기존 CLAUDE.md 읽기
2. 다음이 포함된 보고서 생성:
   - 현재 줄 수 vs 목표
   - 보편적으로 적용 가능한 콘텐츠의 비율
   - 발견된 안티 패턴 목록
   - 개선 권장사항
3. 파일을 수정하지 않고 보고만

## AGENTS.md 처리

사용자가 AGENTS.md 생성/업데이트를 요청하는 경우:

AGENTS.md는 특수 에이전트 동작을 정의하는 데 사용됩니다. CLAUDE.md(프로젝트 컨텍스트용)와 달리 AGENTS.md는 다음을 정의합니다:
- 사용자 정의 에이전트 역할 및 기능
- 에이전트별 지침 및 제약
- 멀티 에이전트 시나리오의 워크플로우 정의

유사한 원칙 적용:
- 집중적이고 간결하게 유지
- 점진적 공개 사용
- 콘텐츠를 포함하는 대신 외부 문서 참조

## 참고 사항

- 포함하기 전에 항상 커맨드가 작동하는지 확인
- 확실하지 않으면 빼기 - 적을수록 좋다
- 시스템 리마인더는 Claude에게 CLAUDE.md가 "관련이 있을 수도 있고 없을 수도 있다"고 알림 - 노이즈가 많을수록 무시됨
- 모노레포는 명확한 WHAT/WHY/HOW 구조에서 가장 큰 이점을 얻음
- 디렉토리별 CLAUDE.md 파일은 더욱 집중되어야 함

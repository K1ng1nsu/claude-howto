# 코드 리팩토링 스킬

Martin Fowler의 *Refactoring: Improving the Design of Existing Code* (2판)에 기반한 체계적인 코드 리팩토링 접근 방식입니다. 이 스킬은 테스트에 의해 뒷받침되는 안전하고 점진적인 변경을 강조합니다.

> "리팩토링은 코드의 외부 동작은 변경하지 않으면서 내부 구조를 개선하는 소프트웨어 시스템 변경 과정입니다." — Martin Fowler

## 핵심 원칙

1. **동작 보존**: 외부 동작은 변경되지 않아야 함
2. **작은 단계**: 작고 테스트 가능한 변경
3. **테스트 주도**: 테스트는 안전망
4. **지속적**: 리팩토링은 일회성 이벤트가 아닌 지속적인 과정
5. **협업적**: 각 단계에서 사용자 승인 필요

## 워크플로우 개요

```
1단계: 리서치 및 분석
    ↓
2단계: 테스트 커버리지 평가
    ↓
3단계: 코드 스멜 식별
    ↓
4단계: 리팩토링 계획 생성
    ↓
5단계: 점진적 구현
    ↓
6단계: 검토 및 반복
```

---

## 1단계: 리서치 및 분석

### 목표
- 코드베이스 구조와 목적 이해
- 리팩토링 범위 식별
- 비즈니스 요구사항에 대한 컨텍스트 수집

### 사용자에게 물을 질문
시작하기 전에 명확히:

1. **범위**: 어떤 파일/모듈/함수를 리팩토링해야 하나요?
2. **목표**: 어떤 문제를 해결하려고 하나요? (가독성, 성능, 유지보수성)
3. **제약**: 변경해서는 안 되는 영역이 있나요?
4. **일정 압박**: 다른 작업을 막고 있나요?
5. **테스트 상태**: 테스트가 존재하나요? 통과하고 있나요?

### 실행
- [ ] 대상 코드 읽고 이해
- [ ] 의존성 및 통합 식별
- [ ] 현재 아키텍처 문서화
- [ ] 기존 기술 부채 마커 기록 (TODO, FIXME)

### 출력
사용자에게 결과 제시:
- 코드 구조 요약
- 식별된 문제 영역
- 초기 권장사항
- **진행 승인 요청**

---

## 2단계: 테스트 커버리지 평가

### 테스트가 중요한 이유
> "테스트 없는 리팩토링은 안전벨트 없는 운전과 같습니다." — Martin Fowler

테스트는 안전한 리팩토링의 **핵심 요소**입니다. 테스트 없이 버그를 도입할 위험이 있습니다.

### 평가 단계

1. **기존 테스트 확인**
   ```bash
   # 테스트 파일 찾기
   find . -name "*test*" -o -name "*spec*" | head -20
   ```

2. **기존 테스트 실행**
   ```bash
   # JavaScript/TypeScript
   npm test

   # Python
   pytest -v

   # Java
   mvn test
   ```

3. **커버리지 확인 (가능한 경우)**
   ```bash
   # JavaScript
   npm run test:coverage

   # Python
   pytest --cov=.
   ```

### 결정 지점: 사용자에게 질문

**테스트가 존재하고 통과하는 경우:**
- 3단계로 진행

**테스트가 없거나 불완전한 경우:**
옵션 제시:
1. 먼저 테스트 작성 (권장)
2. 리팩토링 중에 점진적으로 테스트 추가
3. 테스트 없이 진행 (위험 - 사용자 인정 필요)

**테스트가 실패하는 경우:**
- 중지. 리팩토링 전에 실패한 테스트 수정
- 사용자에게 질문: 먼저 테스트를 수정할까요?

### 테스트 작성 가이드라인 (필요시)

리팩토링되는 각 함수에 대해 테스트가 다음을 커버하는지 확인:
- 행복 경로 (정상 작동)
- 엣지 케이스 (빈 입력, null, 경계)
- 오류 시나리오 (잘못된 입력, 예외)

"red-green-refactor" 사이클 사용:
1. 실패하는 테스트 작성 (red)
2. 통과시키기 (green)
3. 리팩토링

## 3단계: 코드 스멜 식별

### 코드 스멜이란?
코드의 더 깊은 문제의 증상입니다. 버그는 아니지만 코드가 개선될 수 있음을 나타냅니다.

### 확인할 일반적인 코드 스멜

전체 카탈로그는 [references/code-smells.md](references/code-smells.md)를 참조하세요.

#### 빠른 참조

| 스멜 | 징후 | 영향 |
|-------|-------|--------|
| **긴 메서드** | 30-50줄 초과 메서드 | 이해, 테스트, 유지보수 어려움 |
| **중복 코드** | 여러 곳의 동일한 로직 | 여러 곳에서 버그 수정 필요 |
| **큰 클래스** | 너무 많은 책임을 가진 클래스 | 단일 책임 위반 |
| **기능 선망** | 다른 클래스의 데이터를 더 많이 사용하는 메서드 | 낮은 캡슐화 |
| **원시 타입 집착** | 객체 대신 원시 타입 과도 사용 | 누락된 도메인 개념 |
| **긴 매개변수 목록** | 4개 이상의 매개변수를 가진 메서드 | 올바르게 호출하기 어려움 |
| **데이터 덩어리** | 함께 나타나는 동일한 데이터 항목 | 누락된 추상화 |
| **Switch 문** | 복잡한 switch/if-else 체인 | 확장 어려움 |
| **투기적 일반화** "혹시 몰라서" 코드 | 불필요한 복잡성 |
| **죽은 코드** | 사용되지 않는 코드 | 혼란, 유지보수 부담 |

### 분석 단계

1. **자동 분석** (스크립트가 있는 경우)
   ```bash
   python scripts/detect-smells.py <file>
   ```

2. **수동 검토**
   - 체계적으로 코드 살펴보기
   - 각 스멜을 위치 및 심각도와 함께 기록
   - 영향별로 분류 (Critical/High/Medium/Low)

3. **우선순위 지정**
   다음 스멜에 집중:
   - 현재 개발을 막는 것
   - 버그나 혼란을 유발하는 것
   - 가장 많이 변경되는 코드 경로에 영향을 주는 것

### 출력: 스멜 리포트

사용자에게 제시:
- 위치가 포함된 식별된 스멜 목록
- 각각에 대한 심각도 평가
- 권장 우선순위 순서
- **우선순위 승인 요청**

---

## 4단계: 리팩토링 계획 생성

### 리팩토링 선택

각 스멜에 대해 카탈로그에서 적절한 리팩토링을 선택하세요.

전체 목록은 [references/refactoring-catalog.md](references/refactoring-catalog.md)를 참조하세요.

#### 스멜-리팩토링 매핑

| 코드 스멜 | 권장 리팩토링 |
|------------|---------------------------|
| 긴 메서드 | 메서드 추출, 임시 변수를 질의로 대체 |
| 중복 코드 | 메서드 추출, 메서드 올리기, 템플릿 메서드 형성 |
| 큰 클래스 | 클래스 추출, 서브클래스 추출 |
| 기능 선망 | 메서드 이동, 필드 이동 |
| 원시 타입 집착 | 객체로 원시 타입 대체, 타입 코드를 클래스로 대체 |
| 긴 매개변수 목록 | 매개변수 객체 도입, 전체 객체 보존 |
| 데이터 덩어리 | 클래스 추출, 매개변수 객체 도입 |
| Switch 문 | 조건문을 다형성으로 대체 |
| 투기적 일반화 | 계층 구조 축소, 클래스 인라인, 죽은 코드 제거 |
| 죽은 코드 | 죽은 코드 제거 |

### 계획 구조

[templates/refactoring-plan.md](templates/refactoring-plan.md)의 템플릿을 사용하세요.

각 리팩토링에 대해:
1. **대상**: 어떤 코드가 변경될 것인가
2. **스멜**: 어떤 문제를 해결하는가
3. **리팩토링**: 어떤 기법을 적용할 것인가
4. **단계**: 상세한 마이크로 단계
5. **위험**: 무엇이 잘못될 수 있는가
6. **롤백**: 필요한 경우 실행 취소 방법

### 단계적 접근 방식

**중요**: 리팩토링을 단계별로 점진적으로 도입하세요.

**A단계: 빠른 성과** (낮은 위험, 높은 가치)
- 명확성을 위해 변수 이름 변경
- 명백한 중복 코드 추출
- 죽은 코드 제거

**B단계: 구조적 개선** (중간 위험)
- 긴 함수에서 메서드 추출
- 매개변수 객체 도입
- 적절한 클래스로 메서드 이동

**C단계: 아키텍처 변경** (높은 위험)
- 조건문을 다형성으로 대체
- 클래스 추출
- 디자인 패턴 도입

### 결정 지점: 계획을 사용자에게 제시

구현 전:
- 전체 리팩토링 계획 표시
- 각 단계와 그 위험 설명
- 각 단계에 대한 명시적 승인 받기
- **질문**: "A단계를 진행할까요?"

---

## 5단계: 점진적 구현

### 황금률
> "변경 → 테스트 → 통과? → 커밋 → 다음 단계"

### 구현 리듬

각 리팩토링 단계에 대해:

1. **사전 확인**
   - 테스트가 통과 중 (green)
   - 코드 컴파일

2. **하나의 작은 변경**
   - 카탈로그의 메커닉스 따르기
   - 변경을 최소로 유지

3. **확인**
   - 즉시 테스트 실행
   - 컴파일 오류 확인

4. **테스트 통과 (green)**
   - 설명적인 메시지로 커밋
   - 다음 단계로 이동

5. **테스트 실패 (red)**
   - 즉시 중지
   - 변경 실행 취소
   - 무엇이 잘못되었는지 분석
   - 불명확하면 사용자에게 질문

### 커밋 전략

각 커밋은:
- **원자적**: 하나의 논리적 변경
- **되돌릴 수 있음**: 쉽게 되돌리기 가능
- **설명적**: 명확한 커밋 메시지

커밋 메시지 예제:
```
refactor: processOrder()에서 calculateTotal() 추출
refactor: 명확성을 위해 'x'를 'customerCount'로 이름 변경
refactor: 사용되지 않는 validateOldFormat() 메서드 제거
```

### 진행 상황 보고

각 하위 단계 후 사용자에게 보고:
- 수행된 변경사항
- 테스트가 여전히 통과?
- 발생한 이슈
- **질문**: "다음 배치로 계속할까요?"

## 6단계: 검토 및 반복

### 리팩토링 후 체크리스트

- [ ] 모든 테스트 통과
- [ ] 새 경고/오류 없음
- [ ] 코드가 성공적으로 컴파일
- [ ] 동작 변경 없음 (수동 확인)
- [ ] 필요한 경우 문서 업데이트
- [ ] 커밋 기록이 깔끔함

### 메트릭 비교

이전과 이후에 복잡도 분석 실행:
```bash
python scripts/analyze-complexity.py <file>
```

개선 사항 제시:
- 코드 줄 수 변경
- 순환 복잡도 변경
- 유지보수성 지수 변경

### 사용자 검토

최종 결과 제시:
- 모든 변경사항 요약
- 이전/이후 코드 비교
- 메트릭 개선
- 남은 기술 부채
- **질문**: "이 변경사항에 만족하시나요?"

### 다음 단계

사용자와 논의:
- 추가로 해결할 스멜?
- 후속 리팩토링 일정?
- 유사한 변경을 다른 곳에도 적용?

---

## 중요 가이드라인

### 중단하고 질문해야 할 때

다음과 같은 경우 항상 멈추고 사용자와 상의:
- 비즈니스 로직에 대해 확실하지 않을 때
- 변경이 외부 API에 영향을 줄 수 있을 때
- 테스트 커버리지가 부적절할 때
- 중요한 아키텍처 결정이 필요할 때
- 위험 수준이 증가할 때
- 예상치 못한 복잡성을 만났을 때

### 안전 규칙

1. **테스트 없이 리팩토링하지 않음** (사용자가 명시적으로 위험을 인정하지 않는 한)
2. **큰 변경을 하지 않음** - 작은 단계로 나누기
3. **각 변경 후 테스트 실행을 건너뛰지 않음**
4. **테스트가 실패하면 계속하지 않음** - 먼저 수정 또는 롤백
5. **가정하지 않음** - 확실하지 않으면 질문

### 하지 말아야 할 것

- 리팩토링과 기능 추가를 결합하지 않음
- 프로덕션 비상 상황 중에 리팩토링하지 않음
- 이해하지 못하는 코드를 리팩토링하지 않음
- 과도한 엔지니어링 금지 - 단순하게 유지
- 한 번에 모든 것을 리팩토링하지 않음

## 빠른 시작 예제

### 시나리오: 중복이 있는 긴 메서드

**이전:**
```javascript
function processOrder(order) {
  // 150줄 코드:
  // - 중복된 검증 로직
  // - 인라인 계산
  // - 혼합된 책임
}
```

**리팩토링 단계:**

1. **테스트가 존재하는지 확인** for processOrder()
2. **추출** 검증 into validateOrder()
3. **테스트** - 통과해야 함
4. **추출** 계산 into calculateOrderTotal()
5. **테스트** - 통과해야 함
6. **추출** 알림 into notifyCustomer()
7. **테스트** - 통과해야 함
8. **검토** - processOrder()가 이제 3개의 명확한 함수를 조정

**이후:**
```javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
```

name: blog-draft
description: 아이디어와 자료로 블로그 게시물 초안 작성. 사용자가 블로그 게시물을 작성하려고 하거나, 리서치에서 콘텐츠를 만들거나, 기사를 초안 작성할 때 사용합니다. 리서치, 브레인스토밍, 개요 작성, 버전 관리가 포함된 반복적 초안 작성을 안내합니다.
---

## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다. 사용자는 다음을 제공해야 합니다:
- **아이디어/주제**: 블로그 게시물의 주요 개념 또는 테마
- **자료**: URL, 파일, 또는 리서치 참고 자료 (선택 사항이지만 권장)
- **대상 독자**: 블로그 게시물의 대상 (선택 사항)
- **톤/스타일**: 격식, 캐주얼, 기술적 등 (선택 사항)

**중요**: 사용자가 **기존 블로그 게시물**에 대한 업데이트를 요청하는 경우, 0-8단계를 건너뛰고 바로 **9단계**에서 시작하세요. 먼저 기존 초안 파일을 읽은 다음 반복 프로세스를 진행하세요.

## 실행 흐름

다음 단계를 순차적으로 따르세요. **표시된 곳에서 사용자 승인 없이 단계를 건너뛰거나 진행하지 마세요.**

### 0단계: 프로젝트 폴더 생성

1. `YYYY-MM-DD-short-topic-name` 형식을 사용하여 폴더 이름 생성
   - 오늘 날짜 사용
   - 주제에서 짧고 URL 친화적인 슬러그 생성 (소문자, 하이픈, 최대 5단어)

2. 폴더 구조 생성:
   ```
   blog-posts/
   └── YYYY-MM-DD-short-topic-name/
       └── resources/
   ```

3. 진행 전에 사용자에게 폴더 생성을 확인.

### 1단계: 리서치 및 자료 수집

1. 블로그 게시물 디렉토리에 `resources/` 하위 폴더 생성

2. 제공된 각 자료에 대해:
   - **URL**: 가져와서 주요 정보를 `resources/`에 마크다운 파일로 저장
   - **파일**: 읽고 `resources/`에 요약
   - **주제**: 웹 검색을 사용하여 최신 정보 수집

3. 각 자료에 대해 `resources/`에 요약 파일 생성:
   - `resources/source-1-[short-name].md`
   - `resources/source-2-[short-name].md`
   - 등

4. 각 요약에는 다음이 포함되어야 합니다:
   ```markdown
   # 출처: [Title/URL]

   ## 주요 포인트
   - 포인트 1
   - 포인트 2

   ## 관련 인용문/데이터
   - 인용문 또는 통계 1
   - 인용문 또는 통계 2

   ## 주제와의 관련성
   관련성에 대한 간략한 설명
   ```

5. 리서치 요약을 사용자에게 제시.

### 2단계: 브레인스토밍 및 명확화

1. 아이디어와 리서치된 자료를 기반으로 다음 제시:
   - 리서치에서 식별된 **주요 테마**
   - 블로그 게시물의 **잠재적 관점**
   - 다루어야 할 **핵심 포인트**
   - 명확화가 필요한 **정보의 갭**

2. 명확화 질문:
   - 독자들이 얻어가길 바라는 주요 메시지는 무엇인가요?
   - 리서치에서 강조하고 싶은 특정 포인트가 있나요?
   - 목표 길이는? (짧음: 500-800단어, 중간: 1000-1500, 긺: 2000+)
   - 제외하고 싶은 포인트가 있나요?

3. **사용자 응답을 기다린 후 진행.**

### 3단계: 개요 제안

1. 구조화된 개요 생성:

   ```markdown
   # 블로그 게시물 개요: [Title]

   ## 메타 정보
   - **대상 독자**: [who]
   - **톤**: [style]
   - **목표 길이**: [word count]
   - **주요 메시지**: [key message]

   ## 제안된 구조

   ### 훅/서론
   - 오프닝 훅 아이디어
   - 컨텍스트 설정
   - 논제 선언문

   ### 섹션 1: [Title]
   - 핵심 포인트 A
   - 핵심 포인트 B
   - [source]의 지원 증거

   ### 섹션 2: [Title]
   - 핵심 포인트 A
   - 핵심 포인트 B

   [모든 섹션에 대해 계속...]

   ### 결론
   - 핵심 포인트 요약
   - 행동 촉구 또는 마지막 생각

   ## 인용할 출처
   - 출처 1
   - 출처 2
   ```

2. 개요를 사용자에게 제시하고 **승인 또는 수정 요청**.

### 4단계: 승인된 개요 저장

1. 사용자가 개요를 승인하면 블로그 게시물 폴더에 `OUTLINE.md`로 저장.

2. 개요가 저장되었음을 확인.

### 5단계: 개요 커밋 (git 저장소인 경우)

1. 현재 디렉토리가 git 저장소인지 확인.

2. 그렇다면:
   - 새 파일(블로그 게시물 폴더, 리소스, OUTLINE.md) 스테이징
   - `docs: Add outline for blog post - [topic-name]` 메시지로 커밋 생성
   - 원격으로 푸시

3. git 저장소가 아니면 이 단계를 건너뛰고 사용자에게 알림.

### 6단계: 초안 작성

1. 승인된 개요를 기반으로 전체 블로그 게시물 초안 작성.

2. OUTLINE.md의 구조를 정확히 따름.

3. 포함 사항:
   - 훅이 있는 매력적인 서론
   - 명확한 섹션 헤더
   - 리서치의 지원 증거 및 예제
   - 섹션 간 부드러운 전환
   - 메시지가 있는 강력한 결론
   - **인용**: 모든 비교, 통계, 데이터 포인트 및 사실적 주장은 원본 출처를 반드시 인용

4. 블로그 게시물 폴더에 `draft-v0.1.md`로 저장.

5. 형식:
   ```markdown
   # [Blog Post Title]

   *[Optional: subtitle or tagline]*

   [인라인 인용이 있는 전체 콘텐츠...]

   ---

   ## 참고 문헌
   - [1] 출처 1 제목 - URL 또는 인용
   - [2] 출처 2 제목 - URL 또는 인용
   - [3] 출처 3 제목 - URL 또는 인용
   ```

6. **인용 요구사항**:
   - 모든 데이터 포인트, 통계 또는 비교는 인라인 인증이 있어야 함
   - 번호가 매겨진 참조 [1], [2] 등, 또는 명명된 인용 [Source Name] 사용
   - 인용을 끝의 참고 문헌 섹션에 연결
   - 예제: "연구에 따르면 개발자의 65%가 TypeScript를 선호합니다 [1]"
   - 예제: "React는 Vue보다 렌더링 속도가 20% 빠릅니다 [React Benchmarks 2024]"

### 7단계: 초안 커밋 (git 저장소인 경우)

1. git 저장소인지 확인.

2. 그렇다면:
   - 초안 파일 스테이징
   - `docs: Add draft v0.1 for blog post - [topic-name]` 메시지로 커밋 생성
   - 원격으로 푸시

3. 그렇지 않으면 건너뛰고 사용자에게 알림.

### 8단계: 검토를 위한 초안 제시

1. 초안 콘텐츠를 사용자에게 제시.

2. 피드백 요청:
   - 전반적인 인상?
   - 확장 또는 축소가 필요한 섹션?
   - 톤 조정 필요?
   - 누락된 정보?
   - 특정 편집 또는 재작성?

3. **사용자 응답 기다림.**

### 9단계: 반복 또는 마무리

**사용자가 변경을 요청하는 경우:**
1. 요청된 모든 수정사항 기록
2. 다음 조정과 함께 6단계로 돌아가기:
   - 버전 번호 증가 (v0.2, v0.3 등)
   - 모든 피드백 통합
   - `draft-v[X.Y].md`로 저장
   - 7-8단계 반복

**사용자가 승인하는 경우:**
1. 최종 초안 버전 확인
2. 사용자가 요청하면 선택적으로 `final.md`로 이름 변경
3. 블로그 게시물 생성 프로세스 요약:
   - 생성된 총 버전 수
   - 버전 간 주요 변경사항
   - 최종 단어 수
   - 생성된 파일

## 버전 추적

모든 초안은 증분 버전 관리로 보존됩니다:
- `draft-v0.1.md` - 최초 초안
- `draft-v0.2.md` - 첫 번째 피드백 이후
- `draft-v0.3.md` - 두 번째 피드백 이후
- 등

이를 통해 블로그 게시물의 진화를 추적하고 필요시 되돌릴 수 있습니다.

## 출력 파일 구조

```
blog-posts/
└── YYYY-MM-DD-topic-name/
    ├── resources/
    │   ├── source-1-name.md
    │   ├── source-2-name.md
    │   └── ...
    ├── OUTLINE.md
    ├── draft-v0.1.md
    ├── draft-v0.2.md (반복이 있는 경우)
    └── draft-v0.3.md (더 많은 반복이 있는 경우)
```

## 품질 팁

- **훅**: 질문, 놀라운 사실 또는 공감할 수 있는 시나리오로 시작
- **흐름**: 각 문단이 다음 문단과 연결되어야 함
- **증거**: 리서치의 데이터로 주장 뒷받침
- **인용**: 항상 다음에 대한 출처 인용:
  - 모든 통계 및 데이터 포인트 (예: "[Source]에 따르면, 75%가...")
  - 제품, 서비스 또는 접근 방식 간의 비교 (예: "X가 Y보다 2배 빠릅니다 [Source]")
  - 시장 동향, 연구 결과 또는 벤치마크에 대한 사실적 주장
  - 형식이 있는 인라인 인용 사용: [Source Name] 또는 [Author, Year]
- **보이스**: 전체적으로 일관된 톤 유지
- **길이**: 목표 단어 수 준수
- **가독성**: 짧은 문단, 적절한 곳에 불릿 포인트 사용
- **CTA**: 명확한 행동 촉구 또는 생각을 자극하는 질문으로 마무리

## 참고 사항

- 항상 지정된 체크포인트에서 사용자 승인을 기다림
- 기록을 위해 모든 초안 버전 보존
- URL이 제공되면 최신 정보를 위해 웹 검색 사용
- 리소스가 충분하지 않으면 사용자에게 더 요청하거나 추가 리서치 제안
- 대상 독자(기술적, 일반, 비즈니스 등)에 따라 톤 조정

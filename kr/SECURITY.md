# 보안 정책

## 개요

Claude How To 프로젝트의 보안은 우리에게 중요합니다. 이 문서는 보안 관행을 설명하고 보안 취약점을 책임감 있게 신고하는 방법을 설명합니다.

## 지원 버전

다음 버전에 대해 보안 업데이트를 제공합니다:

| 버전 | 상태 | 지원 기한 |
|---------|--------|---------------|
| 최신 (main) | ✅ 활성 | 현재 + 6개월 |
| 1.x 릴리스 | ✅ 활성 | 다음 메이저 버전까지 |

**참고**: 교육용 가이드 프로젝트로서, 기존의 버전 지원보다는 현재의 모범 사례와 문서 보안을 유지하는 데 중점을 둡니다. 업데이트는 메인 브랜치에 직접 적용됩니다.

## 보안 관행

### 코드 보안

1. **의존성 관리**
   - 모든 Python 의존성은 `requirements.txt`에 고정됩니다
   - Dependabot 및 수동 검토를 통한 정기 업데이트
   - 매 커밋마다 Bandit으로 보안 스캔
   - 보안 검사를 위한 Pre-commit 훅

2. **코드 품질**
   - Ruff를 통한 린팅으로 일반적인 문제 발견
   - mypy를 통한 타입 검사로 타입 관련 취약점 방지
   - Pre-commit 훅이 기준을 강제
   - 모든 변경 사항은 병합 전에 검토됨

3. **접근 제어**
   - `main` 브랜치에 브랜치 보호
   - 병합 전 필수 리뷰
   - 병합 전 상태 검사 통과 필수
   - 저장소에 대한 제한된 쓰기 권한

### 문서 보안

1. **예제에 비밀 정보 없음**
   - 예제의 모든 API 키는 플레이스홀더
   - 자격 증명은 절대 하드코딩되지 않음
   - `.env.example` 파일이 필요한 변수 표시
   - 비밀 관리에 대한 명확한 경고

2. **보안 모범 사례**
   - 예제는 안전한 패턴을 시연
   - 문서에 보안 경고 표시
   - 공식 보안 가이드로의 링크
   - 관련 섹션에서 자격 증명 처리 논의

3. **콘텐츠 검토**
   - 모든 문서는 보안 이슈 검토 완료
   - 기여 가이드라인의 보안 고려 사항
   - 외부 링크 및 참조 검증

### 의존성 보안

1. **스캔**
   - Bandit이 모든 Python 코드의 취약점 스캔
   - GitHub 보안 알림을 통한 의존성 취약점 확인
   - 정기적인 수동 보안 감사

2. **업데이트**
   - 보안 패치를 신속히 적용
   - 메이저 버전은 신중히 평가
   - 변경 로그에 보안 관련 업데이트 포함

3. **투명성**
   - 보안 업데이트는 커밋에 문서화
   - 취약점 공개는 책임감 있게 처리
   - 필요시 공개 보안 권고

## 취약점 신고

### 관심 있는 보안 이슈

다음에 대한 신고를 환영합니다:
- **스크립트 또는 예제의 코드 취약점**
- **Python 패키지의 의존성 취약점**
- **모든 코드 예제의 암호화 이슈**
- **문서의 인증/인가 결함**
- **설정 예제의 데이터 노출 위험**
- **인젝션 취약점 (SQL, 명령어 등)**
- **SSRF/XXE/경로 탐색 이슈**

### 범위 외 보안 이슈

다음은 이 프로젝트의 범위를 벗어납니다:
- Claude Code 자체의 취약점 (Anthropic에 신고)
- 외부 서비스 또는 라이브러리의 이슈 (상위 프로젝트에 신고)
- 사회 공학 또는 사용자 교육 (이 가이드에는 해당하지 않음)
- 개념 증명이 없는 이론적 취약점
- 공식 채널을 통해 신고된 의존성 취약점

## 신고 방법

### 비공개 신고 (권장)

**민감한 보안 이슈는 GitHub의 비공개 취약점 신고를 사용해 주세요:**

1. 방문: https://github.com/luongnv89/claude-howto/security/advisories
2. "Report a vulnerability" 클릭
3. 취약점 세부 정보 입력
4. 다음을 포함:
   - 취약점에 대한 명확한 설명
   - 영향을 받는 구성 요소 (파일, 섹션, 예제)
   - 잠재적 영향
   - 재현 단계 (해당하는 경우)
   - 제안하는 수정 사항 (있는 경우)

**다음과 같이 진행됩니다:**
- 48시간 이내에 접수 확인
- 조사 및 심각도 평가
- 수정 사항 개발을 위해 협력
- 공개 일정 조정
- 보안 권고에 귀하를 표시 (익명을 선호하는 경우 제외)

### 공개 신고

민감하지 않은 이슈 또는 이미 공개된 이슈의 경우:

1. **GitHub Issue**를 `security` 레이블로 열기
2. 다음을 포함:
   - 제목: `[SECURITY]` 뒤에 간단한 설명
   - 상세 설명
   - 영향을 받는 파일 또는 섹션
   - 잠재적 영향
   - 제안하는 수정 사항

## 취약점 대응 절차

### 평가 (24시간)

1. 신고 접수 확인
2. [CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document)을 사용하여 심각도 평가
3. 범위 내에 있는지 확인
4. 초기 평가와 함께 연락

### 개발 (1-7일)

1. 수정 사항 개발
2. 수정 사항 검토 및 테스트
3. 보안 권고 작성
4. 릴리스 노트 준비

### 공개 (심각도에 따라 다름)

**심각 (CVSS 9.0-10.0)**
- 즉시 수정 사항 릴리스
- 공개 권고 발행
- 신고자에게 24시간 사전 통보

**높음 (CVSS 7.0-8.9)**
- 48-72시간 내 수정 사항 릴리스
- 신고자에게 5일 사전 통보
- 릴리스 시 공개 권고

**중간 (CVSS 4.0-6.9)**
- 다음 정기 업데이트에 수정 사항 포함
- 릴리스 시 공개 권고

**낮음 (CVSS 0.1-3.9)**
- 다음 정기 업데이트에 수정 사항 포함
- 릴리스 시 권고

### 게시

다음을 포함하는 보안 권고를 게시합니다:
- 취약점 설명
- 영향을 받는 구성 요소
- 심각도 평가 (CVSS 점수)
- 수정 버전
- 해결 방법 (해당하는 경우)
- 신고자 표시 (허가가 있는 경우)

## 신고자를 위한 모범 사례

### 신고 전

- **이슈 확인**: 일관되게 재현할 수 있나요?
- **기존 이슈 검색**: 이미 신고되었나요?
- **문서 확인**: 안전한 사용에 대한 지침이 있나요?
- **수정 사항 테스트**: 제안하는 수정 사항이 작동하나요?

### 신고 시

- **구체적으로 작성**: 정확한 파일 경로와 줄 번호 제공
- **컨텍스트 포함**: 왜 보안 이슈인가요?
- **영향 제시**: 공격자가 무엇을 할 수 있나요?
- **단계 제공**: 어떻게 재현할 수 있나요?
- **수정 사항 제안**: 어떻게 수정하시겠어요?

### 신고 후

- **인내심을 가지세요**: 리소스가 제한적입니다
- **응답하세요**: 후속 질문에 신속히 답변
- **기밀 유지**: 수정 전에 공개적으로 공개하지 마세요
- **협력 존중**: 공개 일정을 따르세요

## 보안 헤더 및 설정

### 저장소 보안

- **브랜치 보호**: 메인 브랜치는 변경에 2명의 승인 필요
- **상태 검사**: 모든 CI/CD 검사가 통과해야 함
- **CODEOWNERS**: 주요 파일에 대한 지정된 리뷰어
- **서명된 커밋**: 기여자에게 권장

### 개발 보안

```bash
# Pre-commit 훅 설치
pre-commit install

# 로컬에서 보안 스캔 실행
bandit -c pyproject.toml -r scripts/
mypy scripts/ --ignore-missing-imports
ruff check scripts/
```

### 의존성 보안

```bash
# 알려진 취약점 확인
pip install safety
safety check

# 또는 pip-audit 사용
pip install pip-audit
pip-audit
```

## 기여자를 위한 보안 가이드라인

### 예제 작성 시

1. **비밀 정보를 절대 하드코딩하지 마세요**
   ```python
   # ❌ 나쁜 예
   api_key = "sk-1234567890"

   # ✅ 좋은 예
   api_key = os.getenv("API_KEY")
   ```

2. **보안 영향에 대해 경고하세요**
   ```markdown
   ⚠️ **보안 주의**: `.env` 파일을 git에 커밋하지 마세요.
   즉시 `.gitignore`에 추가하세요.
   ```

3. **안전한 기본값을 사용하세요**
   - 인증을 기본적으로 활성화
   - 해당하는 경우 HTTPS 사용
   - 입력 검증 및 정제
   - 매개변수화된 쿼리 사용

4. **보안 고려 사항을 문서화하세요**
   - 보안이 중요한 이유 설명
   - 안전한 패턴과 안전하지 않은 패턴 모두 제시
   - 권위 있는 출처로 링크
   - 경고를 눈에 띄게 포함

### 기여 검토 시

1. **노출된 비밀 정보 확인**
   - 일반적인 패턴 스캔 (api_key=, password=)
   - 설정 파일 검토
   - 환경 변수 확인

2. **안전한 코딩 관행 확인**
   - 하드코딩된 자격 증명 없음
   - 적절한 입력 검증
   - 안전한 인증/인가
   - 안전한 파일 처리

3. **보안 영향 테스트**
   - 오용될 수 있나요?
   - 최악의 경우는 무엇인가요?
   - 엣지 케이스가 있나요?
